\section{Introduction}

This project implements two distributed workflows for the Telecom Paris lab
machines. The first one is the main deliverable: a custom MapReduce framework
in Go. The second one is a generic deploy/collect/cleanup workflow used to
start a program on many hosts and collect system information. The MapReduce
system builds a worker binary locally, deploys it over SSH/SCP, assigns input,
executes map and reduce through HTTP, then merges the final result locally.

The project works under the practical constraints of the lab: no root access,
no Docker, shared machines, and frequent host churn. For that reason the
implementation deliberately uses only Go binaries, SSH/SCP, HTTP, and
\texttt{/tmp}. The strongest part of the project is the MapReduce orchestration
itself: worker deployment, phase execution, deterministic partitioning,
fault-aware slot reassignment, and pluggable jobs.

What was achieved:
\begin{itemize}[leftmargin=1.5em]
  \item a complete single-stage MapReduce pipeline with local-file and Common
  Crawl input modes;
  \item a generic deployment script pipeline (\texttt{run.sh});
  \item a Kafka comparison path prepared for later benchmarking;
  \item a validated strong-scaling experiment on one fixed 64-file workload.
\end{itemize}

What remains incomplete:
\begin{itemize}[leftmargin=1.5em]
  \item no second MapReduce stage exists in the current design;
  \item the local-file scheduler still assigns at most one chunk per active slot;
  \item very large Common Crawl wordcount runs exposed memory pressure in the
  current worker map path;
  \item the Kafka experiment has not been executed yet;
  \item the report still lacks a real cross-login validation by another student.
\end{itemize}

The largest \emph{validated} dataset processed for this report is a fixed
64-file corpus (\(833{,}953\) bytes) used for the Amdahl experiment.

\section{How to use}

\subsection{Prerequisites}

\begin{itemize}[leftmargin=1.5em]
  \item Go 1.25+ on the local machine.
  \item SSH key-based access to the lab hosts.
  \item Access to \url{https://tp.telecom-paris.fr/ajax.php}.
  \item For Kafka only: Java 17+ on the remote machines.
\end{itemize}

\subsection{Build and test}

\begin{lstlisting}[style=codeblock]
cd scripts
go test ./...
\end{lstlisting}

\subsection{Run the MapReduce pipeline}

\begin{lstlisting}[style=codeblock]
./mapreduce.sh -job scripts/jobs/wordcount -input data/simple.txt \
  -output result.txt -n 10 -port 9090
\end{lstlisting}

Common Crawl mode:

\begin{lstlisting}[style=codeblock]
./mapreduce.sh -job scripts/jobs/wordcount -commoncrawl \
  -crawl CC-MAIN-2026-21 -files-limit 4 -output result.txt -n 10
\end{lstlisting}

\subsection{Run the deploy/collect pipeline}

\begin{lstlisting}[style=codeblock]
./run.sh
\end{lstlisting}

This script fetches hosts, deploys a simple HTTP server, collects
\texttt{hostname}, \texttt{uptime}, and memory statistics, then cleans up.

\subsection{What must change for another student login}

The MapReduce path is mostly login-agnostic because it deploys workers to
\texttt{/tmp/mr-worker}. The main login-sensitive points are:

\begin{enumerate}[leftmargin=1.5em]
  \item \texttt{run.sh}: the variable \texttt{N} controls how many hosts are
  targeted by the deploy/collect workflow.
  \item \texttt{manifest.json}: field \texttt{n} must match \texttt{N} from
  \texttt{run.sh}.
  \item \texttt{manifest.json}: field \texttt{nfs} must be changed if a student
  wants to use NFS-based file deployment.
  \item \texttt{manifest.json}: the command, collect, and cleanup strings must
  match the program the student wants to launch remotely.
  \item The student must already have passwordless SSH configured for the lab.
\end{enumerate}

Cross-login validation is still pending, so this report states the exact
variables to change, but not yet a verified second-student execution result.

\subsection{Deploy script}

The deploy script path is the simpler of the two systems. \texttt{run.sh}
performs four steps:

\begin{enumerate}[leftmargin=1.5em]
  \item fetch \(N\) available hosts with \codepath{scripts/make_hosts};
  \item execute the commands from \texttt{manifest.json} on each host;
  \item collect the configured remote outputs;
  \item execute cleanup commands even if a previous step fails.
\end{enumerate}

In the current repository state, \texttt{manifest.json} starts a Python HTTP
server on each machine, then collects \texttt{hostname}, \texttt{uptime}, and
\texttt{free -m}. The implementation is intentionally generic: only the
manifest changes, not the deploy tool itself.

\subsection{Map Reduce implementation}

\subsubsection{Design}

The MapReduce system is client-orchestrated. There is no permanent master
inside the cluster. Instead, the local machine:

\begin{enumerate}[leftmargin=1.5em]
  \item reads \texttt{hosts.txt};
  \item builds a Linux worker binary with the selected job already linked in;
  \item deploys that binary to every candidate host;
  \item starts each worker as an HTTP server;
  \item assigns input, broadcasts phases, and merges the final output locally.
\end{enumerate}

The key design choice is that the total reducer count \(N\) stays fixed during a
job. This matters because the partition function is
\[
\mathrm{FNV32a}(key) \bmod N.
\]
If a machine dies, the coordinator preserves the logical slot number and
reassigns that slot to a spare or to a surviving worker host.

\subsubsection{Input splitting and dispatch}

The project supports two input modes.

\paragraph{Local-file mode.}
The client splits the file into chunks of at most 64 MB, preferably on newline
boundaries. This is the ``splitting'' phase of the assignment. The current
limitation is important: the main path assigns at most one chunk per active
slot, so if the file produces more than \(N\) chunks, the extra chunks are not
yet scheduled.

\paragraph{Common Crawl mode.}
The client resolves WET URLs and assigns them round-robin. Slot \(i\) receives
URL indices \(i, i+N, i+2N,\ldots\). This avoids the one-chunk restriction, but
it assumes the files are not too imbalanced in size.

\subsubsection{Timing of each phase}

The code reports explicit timings for:
\begin{itemize}[leftmargin=1.5em]
  \item map;
  \item reduce;
  \item result collection;
  \item total compute time.
\end{itemize}

Split and load happen before the compute timer. Shuffle is partly embedded in
reduce, because reducers fetch their peer buckets during \texttt{/reduce}. The
project therefore has one measured MapReduce stage:
\[
\text{split/load} \rightarrow \text{map} \rightarrow \text{shuffle+reduce} \rightarrow \text{collect}.
\]

\subsubsection{Storage and communication}

Intermediate data uses both memory and disk:
\begin{itemize}[leftmargin=1.5em]
  \item map first builds in-memory structures
  (\texttt{map[string][]string});
  \item bucketized intermediate files are then written to node-local disk under
  \texttt{/tmp};
  \item reduce reads those bucket files back and rebuilds grouped values in
  memory.
\end{itemize}

The system does \textbf{not} use FTP. Communication is:
\begin{itemize}[leftmargin=1.5em]
  \item SSH/SCP for deployment and cleanup;
  \item HTTP over TCP for worker control and shuffle;
  \item HTTP for Common Crawl downloads.
\end{itemize}

\subsubsection{Threads and concurrency}

In Go, concurrency is implemented with goroutines. They are used in three main
places:
\begin{enumerate}[leftmargin=1.5em]
  \item bounded-parallel SSH/SCP fan-out in
  \codepath{scripts/internal/remote};
  \item concurrent phase broadcasts, health checks, and result fetches in the
  orchestrator;
  \item concurrent peer fetches during reduce inside the worker.
\end{enumerate}

Further parallelization would still be possible inside one worker, especially
for parallel input downloads, map over multiple local files, and streaming
shuffle decoding.

\subsubsection{Crash behavior and remaining problems}

The coordinator tracks logical slots rather than binding forever to one host. If
a host fails, the slot can be rebound to a spare host or to a surviving active
worker. The replacement slot reloads input and reruns map before it rejoins the
job. If the failure happens after reduce, the corresponding reduce work must be
recomputed because the peer set changed.

The main remaining problems are:
\begin{itemize}[leftmargin=1.5em]
  \item local-file scheduling beyond \(N\) chunks is incomplete;
  \item map and shuffle are still memory-heavy for large wordcount jobs;
  \item there is no durable replicated intermediate state;
  \item orchestrator-level experiments at very large node counts are sensitive to
  SSH/network instability.
\end{itemize}

\subsubsection{Optimization ideas}

The most useful next optimizations would be:
\begin{enumerate}[leftmargin=1.5em]
  \item streaming map output directly into bucket files instead of materializing
  everything in memory first;
  \item a local combiner for associative jobs such as wordcount;
  \item true multi-chunk scheduling in local-file mode;
  \item parallel final merge on the client;
  \item bucket replication if stronger fault tolerance is needed.
\end{enumerate}

\subsection{Kafka}

The Kafka path under \codepath{kafka/*} is intentionally separate from the main
Go implementation. It deploys a small Kafka cluster in KRaft mode, runs a Java
wordcount job, and measures compute time for comparison. Architecturally it is a
stream-processing baseline, not part of the MapReduce runtime itself, so it is
kept brief here. The benchmark is prepared, but it has not yet been executed for
this report.

\section{Experiments}

\subsection{Methodology}

The first idea was to run wordcount on 64 Common Crawl WET files for the Amdahl
plot. In practice, that workload was not stable enough for this environment:
large wordcount runs exposed memory pressure in the worker map path. For that
reason, the validated scaling experiment was redone on a fixed 64-file corpus
(\(833{,}953\) bytes) listed in \codepath{experiments/amdahl/go64_urls.txt}.
Each file is fetched from \texttt{raw.githubusercontent.com}, so the workload is
fixed and reproducible.

The final validated sweep used the same algorithm and the same 64-file dataset,
then varied only the number of active nodes. That is the correct methodology for
Amdahl's law.

overhead overwhelms the useful work.

\subsection{Amdahl's Law}

The correct reference for Amdahl speedup is the 1-node run of the same
algorithm:
\[
S(N) = \frac{T(1)}{T(N)}.
\]
So the baseline is the 1-node MapReduce run, not the 2-node run and not a
separate sequential implementation.

For this dataset, the measured curve rises from 1 to 8 nodes and then bends
strongly downward. This still validates the qualitative expectation behind
Amdahl's law:
\begin{itemize}[leftmargin=1.5em]
  \item first, parallel work dominates and speedup rises;
  \item then communication, synchronization, and the serial merge cost dominate;
  \item finally the system stops scaling and can even slow down.
\end{itemize}

If only the first four points (1, 2, 4, 8) are used, the measured curve is
compatible with an effective parallel fraction of about \(p \approx 0.83\).
That estimate is useful for the ``good'' scaling region. However, the larger
node counts show that one global \(p\) is not enough to describe the full
system once reduce and orchestration costs dominate.

\section{Conclusion}

The project successfully implements a coherent distributed MapReduce system in
Go, together with a reusable deployment pipeline and a prepared Kafka
comparison path. The main technical success is the detailed MapReduce runtime:
worker build injection, deployment, HTTP coordination, slot-preserving recovery,
and pluggable jobs all work end to end.

For the report experiments, the validated maximum dataset processed was the
fixed 64-file corpus used in the strong-scaling sweep. The measured results show
that the system scales well only up to a modest number of nodes for wordcount.
The best compute time was obtained at 8 nodes; after that, the reduce phase
dominates and speedup collapses.

In short:
\begin{itemize}[leftmargin=1.5em]
  \item the project works and is technically complete as a single-stage
  MapReduce system;
  \item the main remaining engineering work is scalability of the map/shuffle
  implementation, especially memory use and high-node-count reduce behavior;
  \item the Kafka comparison and cross-login validation still need to be added
  before the report is fully final.
\end{itemize}
